# 采集服务化拆分设计草案

> **文档定位**：本草案只做选型与设计，不动代码。供架构评审决定是否把"课程采集"从 `web-backend` 单体中拆出。
> **触发**：用户确认本工作空间无独立采集方案文件后，已收敛出 `docx/采集任务方案计划书.md`（功能方案）；本草案回答"该功能能否/应如何抽成独立项目"。
> **版本**：v0.1（评审草案）— 2026-11-11
> **关联文档**：`docx/采集任务方案计划书.md`（功能方案）、`应用拆分与开发分期.md`（整体架构）、根 `任务计划书.md`（网关安全）

---

## 1. 背景与动机

### 1.1 当前落点
采集逻辑全部在 `web-backend` 单体中：
- `app/api/course.py`：源/任务/运行/回滚/metrics/kp 审核等约 16 个端点。
- `app/services/crawl.py`（~530 行）：调度、`run_job`、`intake`、预算停止、指标。
- `app/services/crawl_fetch.py`（~195 行）：SSRF 抓取、本地读、JSON 中→英映射、解析。
- 入库目标：`course_kb` + `course_kb_embeddings` + `exam_paper_intake` + `kp_node` + `question_kp`。

### 1.2 为什么考虑拆
- 采集天然是"重 IO + 重调度 + 可能重 LLM"的工作负载，与 `web-backend` 的"请求-响应"主链路混在一起，故障面耦合、扩缩容无法按需独立。
- 非结构化 LLM 抽取环节（M5-2 缺口）一旦接入，会出现长耗时抽取 worker 池、模型配额隔离等诉求，单体里更难隔离。
- 多源适配器（教材/网页/视频/题库包）持续增加，独立演进更清晰。

### 1.3 为什么现在不强行拆
- M5 功能尚未稳定（非结构化 LLM 抽取未接通、App 真机未验），当前体量小（~700 行）。
- 过早服务化会放大返工。建议**收尾 M5 → 再做内部逻辑分包（A 形态）→ 视平台化诉求升级为独立部署单元（B 形态）**。

---

## 2. 形态选型

| 形态 | 描述 | 可行性 | 代价 / 冲突 |
|------|------|:--:|------|
| **A. 内部逻辑分包** | monorepo 内把 `crawl*` 抽成 `crawl-service/` 子包，仍由 `web-backend` 调用或同镜像部署 | ✅ 极易 | 仅移动代码+改 import，低风险，理清边界 |
| **B. 独立部署单元（web 写域）** | 新容器/镜像，部署在 137，复用同一 `course_kb` 写授权与 137 网络，独立扩缩容 | ✅ 可行 | 新增 compose 服务、网络别名、健康检查；网关加路由/上游；复制 LLM/embed env |
| **C. 完全独立微服务、跨域直写** | 新服务直接写 `course_kb`、与 web 平级 | ⚠️ 需重设计 | **违背单写者原则**（见 §4），不推荐 |

**草案结论**：评审通过后再做 **B 形态**；落地前先用 **A 形态**理清边界。

---

## 3. 目标架构（B 形态草案）

```
[edu-lb/nginx] --/admin/* 静态--> web-front
              --location / ---> [网关 gateway] --/api/admin/course/*--> web-backend (鉴权 + 入库)
                                        --/api/admin/crawl/* --> crawl-service (采集域全部职责)
[137] crawl-service 容器(network-alias: crawl-service)
        ├─ 源/任务/运行/回滚/metrics/kp 审核 API（迁自 course.py 采集部分）
        ├─ crawl.py 调度 + crawl_fetch.py 抓取解析
        └─ 入库：经 web-backend 内部 ingest 接口（见 §4），不直接持 course_kb 写权
[106] postgres(pgvector)  ← 仅 web-backend 写 course_kb（单写者不变）
```

---

## 4. 单写者原则处理（核心难点）

### 4.1 现状约束
计划书 L6 明确：**`course_kb` 是 `web-backend` 与 `agent-backend` 之间的单一数据源，web-backend 单写、agent 只读**。任何"第二个写者"都破坏一致性。

### 4.2 候选方案
- **方案 1（放宽写者清单）**：把 `crawl-service` 定性为"web 写域子服务"，与 `web-backend` 并列列为 `course_kb` 授权写者。需更新架构文档的写者清单，轻微放宽原原则。
- **方案 2（推荐）：crawl-service 不直写，经 web-backend 入库**。`crawl-service` 只负责"抓取+解析+调度+可观测"，把解析出的 `items` 通过 `web-backend` 的**内部 ingest 接口**（仅网关内网/白名单可调用）写入 `course_kb`。单写者原则零破坏，代价是一次内网 RPC。
- **方案 3（共享库）**：把入库逻辑抽成共享库，crawl-service 与 web-backend 都依赖，写入授权仍归 web 域统一管控。

**草案推荐方案 2**：单写者原则不动，crawl-service 纯做采集引擎；若追求零 RPC 再退回方案 1 并显式更新写者清单。

### 4.3 内部 ingest 接口契约（草案）
```
POST /internal/ingest   (仅网关→web-backend 内网链路，B 端不可直接达)
  body: {
    "source_ref": "crawl_run:<run_id>",
    "items": [ {...normalize_item 认的英文字段...} ],
    "mode": "P1" | "P2",
    "tenant_id": "school_pilot_01"
  }
  → 复用现有 crawl_intake.intake 逻辑（去重/预算/双写 embeddings/落 exam_paper_intake）
  → 返回 { inserted, duplicated, failed, paper_id }
```
> 该接口即现有 `intake` 的 HTTP 化，crawl-service 与当前 `run_job` 内部调用同一函数，语义一致。

## 6. 部署 / 网关改动清单（B 形态）

| 项 | 改动 | 备注 |
|----|------|------|
| `docker-compose.yml` | 新增 `crawl-service` 服务（build `./crawl-service`，端口如 `8003:80`） | 与 edu-web-backend 同 `edu-net` |
| 网络别名 | 容器 `--network-alias crawl-service`（**必带**，否则网关 DNS 解析不到，踩过坑） | 同 web-backend 写法 |
| 网关 `config.yaml` | 新增上游 `http://crawl-service:8000` + 路由 `/api/admin/crawl/*` | 网关上游写死别名，须显式加 |
| `deploy/nginx.conf` | **通常不动**（B 端 API 走 `location /`→网关；仅当前端静态独立才需加 `/admin/crawl/` 反代） | 静态 SPA 与 API 路由分离，见整体架构 |
| env | `DATABASE_URL`（指向 106，137→106 已放行复用）、`LLM_API_KEY`、如需自摄取 embed 则 `EMBED_*` | 采用方案 2 时 crawl-service 不需 embed |
| 健康检查 | 暴露 `/healthz`（db+kafka 探针，复用现有模式） | |
| 发版 | 扩展 `deploy/publish_backend.sh` 加 `crawl` 选项；回滚点 `edu-crawl-service:bak-*` | 部署脚本统一落 `/opt/deploy` |
| 迁移 | 容器无 psql，仍走 asyncpg runner 落 `/opt/deploy`（采集域无新表则无需） | |

### 6.1 数据层网络
106 的 pg_hba 仅放行 137（124.221.253.137）。crawl-service 部署在 137 即可复用现有白名单；**若部署到新主机，需先在 106 pg_hba 加白名单**，否则连不上。

### 6.2 灰度与回滚
- **双跑过渡**：web-backend 的 `/course/*` 采集端点保留，`crawl-service` 并行上线，前端逐步切到 `/crawl/*`。
- **回滚**：停 crawl-service 容器 + 网关移除 `/crawl/*` 路由，即恢复 web-backend 旧链路；回滚点 `bak-*` 兜底镜像。
- **数据零风险**：采用方案 2 时入库仍过 web-backend，course_kb 不引入新写者，回滚不涉及数据迁移。

## 7. 风险与决策点

| 风险 | 说明 | 缓解 |
|------|------|------|
| 单写者原则放宽 | 若选方案 1，需评审更新写者清单 | 草案推荐方案 2，零破坏 |
| 跨服务调用延迟/故障 | crawl-service→web-backend ingest 一次 RPC | 内网同机，延迟可忽略；web-backend 不可用时采集失败可重试（沿用 `run.error`/`retry`） |
| 网关路由改动影响面 | 改 config.yaml 影响全链路 | 新增独立前缀 `/crawl/*`，不触动现有 `/course/*` |
| embedding 一致性 | 入库双写 embeddings 仍在 web-backend 完成（方案 2），无新增风险 | — |
| 过早服务化返工 | M5 未完全稳定 | 先 A 形态理清边界，再升级 B |
