# 步骤级归因落地计划书（Schema v1 → 全链路实施）

> **定位**：本计划书把《步骤级归因标注Schema-v1.md》从设计稿变成可执行工程，覆盖 数据模型 → 内容标注 → 判分算法 → 过程采集 → 聚合报告 → 评测验收 六段全链路。
> **对齐**：任务编号 S1–S6，挂接《应用拆分与开发分期.md》P1/P2/P3 与《试点校效果验证方案.md》；ROADMAP 中对应"①题库恢复"与新增线。
> **起草**：2026-10-23 · **状态**：待评审（已按实际落地重排对齐，2026-10-23）
> **一句话目标**：让"第 N 步因为什么错"从 PPT 卖点变成 数据库里可查询、报告里可展示、标书里可举证 的事实。

## 二、分任务明细

### S1｜Schema 与迁移（P0 级，阻塞一切）

| 项 | 内容 |
|---|---|
| **目标** | 让"步骤"成为数据库一等公民；旧数据零破坏 |
| **关键任务** | ① **采用独立宽表 `course_kb_steps`**（已在 106 库建表，非 Schema v1 的 JSONB 方案，以本计划书为准）：每题一行级步骤，字段 `step_kind`(option/blank/subq/procedure/single)、`label`、`text`、`is_correct`(仅 option)、`kp_code`、`kp_name`、`kp_source`(manual/question)、`confidence`，教学深度列 `explanation`(详解+知识点串联)、`error_reason`(常见错误原因)；**归因映射**（S3 零成本查表燃料）：客观题 `distractor_map`（错项→wrong_step+error_type+reason+correction）、填空 `wrong_value_map`、解答题 `typical_errors`（每步 error_type+reason+correction+evidence_hint）——落 `course_kb_steps` 扩展列或题目级 JSONB；② `kb_knowledge_points` 加 `understanding TEXT`、`memory TEXT`、`analogy TEXT`（**prerequisites 复用既有独立表 `kb_kp_prerequisites`，不再单列**）；③ `wrong_questions` 加 `wrong_step_no INT`、`error_type VARCHAR(16)`、`evidence TEXT`、`attribution_source VARCHAR(8)`；④ 新表 `student_step_errors`（student_id/tenant_id/question_id/step_no/error_type/attribution_source/occurred_at，索引 student_id+occurred_at、error_type）；⑤ SQL 迁移脚本（106 库 pgvector/pg16 执行，可回滚）；⑥ `import_bank.py` 增加 `步骤` 列映射（拆分回填 `course_kb_steps`）+ **列数校验闸门**（列数≠表头即拒收该行并报告，顺手修复 demo CSV 引号问题与假元数据） |
| **验收标准** | ✅ 宽表 `course_kb_steps` 已在 106 库建表且 213 题步骤可读、索引命中（step_kind/kp_code）；✅ `kb_knowledge_points` 已加 understanding/memory/analogy 列；✅ `import_bank.py --dry-run` 对含步骤的样例 CSV 校验通过、对错位 CSV 明确拒收；✅ pytest：导入器列校验 + 宽表读写 + 归因映射结构各 ≥1 用例；✅ 教学深度字段（understanding/memory/analogy/explanation/error_reason）gen_pedagogy 可续跑幂等 |
| **依赖** | 无（起点）。106 库连接可用（`.env` DATABASE_URL） |
| **风险** | 106 是生产数据层（137 从库拓扑），迁移必须低峰执行 + 先备份 `pg_dump course_kb kb_knowledge_points wrong_questions` |

### S3｜judge v2 三路分流（算法核心）

| 项 | 内容 |
|---|---|
| **目标** | 判分从"对错布尔"升级为"首错步骤+错因+证据"；客观题零 LLM 成本 |
| **关键任务** | ① 分流路由：选择题→查 `distractor_map[所选]`（命中即定案，不花 token）；填空题→归一化匹配 `wrong_value_map`（未命中落 LLM 兜底）；解答题→LLM 对齐参考 steps；② `_JUDGE_SYSTEM` 重写：输入=题目+参考 steps+学生作答，强制 JSON 输出 `{correct, first_wrong_step, error_type, evidence, comment}`，error_type 限 taxonomy 七类+unknown；③ 参考步骤优先取标注库，无标注题 LLM 现场生成并**顺手落库**（analysis→steps 自动沉淀，跑一题攒一题）；④ 低置信/对不齐 → `error_type="unknown"` 入人工复核队列（**不硬猜**）；⑤ `emit_student_event` 载荷扩展：加 `first_wrong_step/error_type/attribution_source/evidence`（Kafka 事件向后兼容，旧消费者忽略新字段）；⑥ dev 模式（无 LLM）同步支持查表路径——**S 档小模型/无模型学校也能跑客观题归因**（BYOM 弱算力卖点） |
| **验收标准** | ✅ pytest：三路分流各 ≥2 用例（含 distractor_map 命中不触发 LLM 的断言、unknown 兜底断言）；✅ 用 Schema v1 §3 三题构造学生错答样本，judge v2 输出的 wrong_step/error_type 与标注一致；✅ 客观题路径 P95 延迟 <50ms（纯查表）；✅ 事件载荷新字段过 web-backend 消费端联调 |
| **依赖** | S1（字段落点）、S2 首批（参考 steps 燃料） |
