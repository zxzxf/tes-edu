## 二、整体设计

### 2.1 两个正交的隔离维度
- **租户（tenant_id，既有）**：学校/机构级数据隔离，网关 `require_tenant` 强制。是"数据归谁"的边界。
- **区域（region_id，新增）**：华东/华北/华中/华南/西南/西北/东北（全国七大区），是平台运营视角的**粗粒度数据权限作用域**。平台管理员/区域管理员可按 region 过滤可见的租户/学校；学校/教师/家长的 region 由其所属租户派生。

二者正交：一个 region 内含多个 tenant；权限校验先按 region 收窄范围，再按 tenant 隔离。

### 2.2 经典后台权限模型（菜单树 + 角色授权 + 按钮码）
采用国内后台通用的"菜单+角色+权限码"三元模型（RuoYi/Sa-Token 范式），与用户的"新建/修改/删除菜单 + 按钮级控制"表述完全对应：
1. **菜单树**：`sys_menu`（目录 DIR / 菜单 MENU / 按钮 BUTTON 三类节点）。
2. **角色授权**：`sys_role_menu` 把角色与菜单（含其下按钮）绑定。
3. **按钮级控制**：按钮节点带 `permission_code`（如 `system:menu:add`）；前端按码显隐按钮，后端 API 按码放行。

### 2.3 权限引擎（替换硬编码）
- 废弃 `rbac.py` 的 `ROLE_MODULES` 硬编码映射，改为 `get_user_permissions(user_id)` 从 `sys_role_menu` 聚合出用户的 `permission_code` 集合（含菜单节点与按钮节点）。
- 新增依赖 `require_perm(code)`：不在集合内 → `403`。`require_role` 保留做粗粒度兼容。
- JWT 仍只带 `uid/role/tenant_id`；`permission_code` 集合由 web-backend 在请求期从缓存（Redis）或 DB 解析，避免 token 膨胀且支持授权变更实时生效（清缓存即可）。

### 2.4 系统服务（MCP 厂商）的"互不干扰"隔离
> 这是需求里最硬的一条：**每个厂商的数据服务相互独立，互不干扰**。

实现三层隔离：
1. **逻辑隔离（必做）**：所有厂商相关数据表带 `vendor_id` 分区列；数据访问层（DAO）统一注入 `WHERE vendor_id = :current_vendor`，不可绕过（集中 query builder，禁止裸 SQL）。
2. **凭证隔离（必做）**：每厂商独立 AES-256-GCM 加密凭证（`credential_enc` + 每厂商数据密钥，或 KMS 每厂商数据密钥），单厂商凭证泄露不波及其它。
3. **物理隔离（可选/按厂商开启）**：`isolation_mode=physical` 时，厂商数据落独立 Postgres schema `vendor_<id>`、或独立 Redis keyspace `v:<id>:*`、或独立对象存储前缀 `s3://bucket/vendor-<id>/`。

MCP 网关按 `vendor_id` 把请求路由到该厂商的数据服务实例（用其隔离连接），**厂商 A 的数据服务实例永远不触达厂商 B 的命名空间**。

### 2.5 设计决策记录（由设计方自研判，无需用户逐条确认）
> 用户在需求评审时授权"自己去分析"下列边界问题，以下为最终裁定，已同步进第四节矩阵与任务计划。

- **D1 · region_admin 不访问系统服务（MCP 厂商）**：厂商的 endpoint / 凭证属**平台级安全资产**，区域管理员只需管本区域学校与运营数据，无必要接触且会扩大凭证泄露面。故「系统设置 → 系统服务(MCP 厂商)」**仅 admin 可管**（矩阵中 region_admin = ❌）。如未来需要区域级"查看所辖学校已分配厂商的运行状态"，可后续加**只读视图（不暴露 base_url / 凭证）**，本期不做。
- **D2 · 学生不进 Web 后台**：学生为 C 端 App 用户，Web 管理后台不分配任何菜单角色；parent↔student 绑定关系在 App 域处理，本计划不覆盖。
- **D3 · 废弃 researcher 角色**：原 `rbac.py` 的 `RESEARCHER` 从未落地菜单授权，其"教研内容 / 合规初审"能力已可由 **admin（全权）+ teacher（本班教研）/ region_admin（本区域合规）** 覆盖，故五角色（admin/region_admin/school/teacher/parent）即可，不再保留 researcher。
- **D4 · 区域七大区一次性铺满**：华东/华北/华中/华南/西南/西北/东北，种子数据全量写入；`region_id` 作为数据作用域过滤键，**非强制层级**（parent_id 字段预留但本期不启用多级区域树）。
- **D5 · 权限引擎以 DB 驱动替换硬编码**：`ROLE_MODULES` 仅作过渡兼容，`require_role` 保留；最终授权以 `sys_role_menu` 聚合出的 `permission_code` 集合为准，JWT 不膨胀、授权变更经 Redis 缓存即时生效（详见 T-AM2）。
- **D6 · MCP 厂商隔离默认 logical，physical 按需开启**：绝大多数厂商用 `vendor_id` 逻辑分区 + 每厂商独立加密凭证即可满足"互不干扰"；`isolation_mode=physical`（独立 schema / keyspace / 存储前缀）仅对高隔离需求厂商开启，避免无谓运维复杂度。
- **D7 · 认证归属裁定（解决 §九 P1）**：**web-backend 作为后台用户权威库**——`sys_user` 同时存密码哈希与角色/菜单映射，`/login` 校验密码后由 web-backend 签发 JWT，**沿用网关现有同一对 RSA 密钥**（`secrets/jwt_{public,private}.pem`），避免密钥分裂导致网关验签失败；网关继续负责 C 端（学生 App）登录与 `tenant_id` 注入。如此 T-AM1「替换 `_FAKE_USERS` 为 DB 查询」在生产成立，且 C 端链路零改动。

## 三、数据模型（PostgreSQL，扩展原方案第五节）

```sql
-- 1) 后台用户（替换 auth.py 的 _FAKE_USERS）
CREATE TABLE sys_user (
    user_id     VARCHAR(64)  PRIMARY KEY,
    username    VARCHAR(64)  NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,          -- bcrypt/argon2，禁明文
    tenant_id   VARCHAR(64),                       -- 平台角色可空
    region_id   VARCHAR(64),                       -- 区域管理员/平台角色按此过滤
    status      SMALLINT     DEFAULT 1,           -- 1 启用 / 0 禁用
    created_at  TIMESTAMPTZ  DEFAULT now()
);

-- 2) 角色（新增 REGION_ADMIN 区域管理员；废弃 RESEARCHER；student 不进 Web 菜单角色，仅 App 端用户类型）
CREATE TABLE sys_role (
    role_id     VARCHAR(64)  PRIMARY KEY,
    role_code   VARCHAR(32)  NOT NULL UNIQUE,     -- admin/region_admin/school/teacher/parent
    role_name   VARCHAR(64)  NOT NULL,
    tenant_id   VARCHAR(64),                       -- 租户级角色（如某校 teacher）；平台角色空
    region_id   VARCHAR(64),                       -- 区域管理员绑定所辖区域
    remark      TEXT,
    created_at  TIMESTAMPTZ  DEFAULT now()
);

-- 3) 用户-角色（一个用户在某租户下可有多角色）
CREATE TABLE sys_user_role (
    user_id VARCHAR(64) NOT NULL,
    role_id VARCHAR(64) NOT NULL,
    tenant_id VARCHAR(64),
    PRIMARY KEY (user_id, role_id, tenant_id)
);

-- 4) 菜单树（DIR/MENU/BUTTON 三类；BUTTON 节点带 permission_code）
CREATE TABLE sys_menu (
    menu_id        VARCHAR(64) PRIMARY KEY,
    parent_id      VARCHAR(64),                    -- 根节点为空
    menu_name      VARCHAR(64) NOT NULL,
    menu_type      VARCHAR(8)  NOT NULL,           -- DIR / MENU / BUTTON
    path           VARCHAR(128),                   -- 前端路由
    component      VARCHAR(128),                   -- 前端组件
    icon           VARCHAR(64),
    sort           INT          DEFAULT 0,
    permission_code VARCHAR(64),                   -- 按钮级权限码，如 system:menu:add
    visible        BOOLEAN      DEFAULT TRUE,
    status         SMALLINT     DEFAULT 1,
    tenant_id      VARCHAR(64)                      -- 平台菜单空；租户可定制时填
);

-- 5) 角色-菜单授权（含其下按钮权限）
CREATE TABLE sys_role_menu (
    role_id VARCHAR(64) NOT NULL,
    menu_id VARCHAR(64) NOT NULL,
    PRIMARY KEY (role_id, menu_id)
);

-- 6) 区域（全国七大区：华东/华北/华中/华南/西南/西北/东北）
CREATE TABLE sys_region (
    region_id   VARCHAR(64) PRIMARY KEY,
    region_code VARCHAR(32) NOT NULL UNIQUE,       -- EAST/NORTH/CENTRAL/SOUTH/SOUTHWEST/NORTHWEST/NORTHEAST
    region_name VARCHAR(64) NOT NULL,             -- 华东/华北/华中/华南/西南/西北/东北
    parent_id   VARCHAR(64),
    sort        INT          DEFAULT 0
);

-- 7) 系统服务厂商（MCP 厂商注册表）
CREATE TABLE sys_service_vendor (
    vendor_id     VARCHAR(64) PRIMARY KEY,
    vendor_name   VARCHAR(128) NOT NULL,
    vendor_type   VARCHAR(32) NOT NULL,           -- aliyun/tencent/ark/deepseek/custom...
    base_url      TEXT,
    auth_type     VARCHAR(32),                    -- apikey/oauth/aksk
    credential_enc BYTEA,                          -- AES-256-GCM 加密凭证
    status        SMALLINT     DEFAULT 1,
    region_id     VARCHAR(64),
    tenant_id     VARCHAR(64),
    created_at    TIMESTAMPTZ  DEFAULT now()
);

-- 8) 每厂商独立数据服务实例（互不干扰的核心）
CREATE TABLE mcp_service_instance (
    instance_id    VARCHAR(64) PRIMARY KEY,
    vendor_id      VARCHAR(64) NOT NULL REFERENCES sys_service_vendor(vendor_id),
    service_name   VARCHAR(128) NOT NULL,
    data_namespace VARCHAR(128) NOT NULL,         -- schema / keyspace / 存储前缀
    connection_enc BYTEA,                         -- 每实例独立连接/凭证（再加密一层）
    isolation_mode VARCHAR(16) NOT NULL DEFAULT 'logical', -- logical / physical
    status         SMALLINT     DEFAULT 1,
    created_at     TIMESTAMPTZ  DEFAULT now()
);
-- 所有厂商业务数据表须带 vendor_id 分区列（数据访问层强制注入）
```

**种子数据**：7 区域（华东/华北/华中/华南/西南/西北/东北）、5 角色（admin/region_admin/school/teacher/parent；student 为 App 端用户类型不进 Web 菜单角色、researcher 已废弃）、默认菜单树（系统设置 → 菜单管理/角色管理/区域管理/系统服务管理；区域运营 → 学校管理/教研内容/学情看板/错题本/自动组卷/教师批改/家长周报/合规审核）、admin 与 region_admin 账号（密码 bcrypt）。

## 四、角色 × 菜单权限矩阵（每角色菜单权限区别）

| 模块（菜单） | admin（管理员） | region_admin（区域管理员） | school（学校） | teacher（教师） | parent（家长） |
|---|:--:|:--:|:--:|:--:|:--:|
| 系统设置 → 菜单管理 | ✅(全) | ❌ | ❌ | ❌ | ❌ |
| 系统设置 → 角色管理 | ✅ | ❌ | ❌ | ❌ | ❌ |
| 系统设置 → 区域管理 | ✅ | ❌ | ❌ | ❌ | ❌ |
| 系统设置 → 系统服务(MCP厂商) | ✅ | ❌ | ❌ | ❌ | ❌ |
| 区域运营 → 学校管理 | ✅ | 本区域 | 本校 | ❌ | ❌ |
| 教研内容管理 | ✅ | 本区域 | 本校 | 本班 | ❌ |
| 学情看板 | ✅ | 本区域 | 本校 | 本班 | 子女 |
| 错题本 | ✅ | 本区域 | 本校 | 本班 | 子女 |
| 自动组卷 | ✅ | 本区域 | 本校 | ✅ | ❌ |
| 教师批改 | ✅ | 本区域 | 本校 | ✅ | ❌ |
| 家长周报 | ✅ | 本区域 | — | ✅(发) | ✅(看) |
| 合规审核 | ✅ | 本区域 | 本校 | ❌ | ❌ |

> **关键差异**：
> - **admin（管理员）** 拥有「系统设置」全部（菜单/角色/区域/系统服务）及全域运营权限。
> - **region_admin（区域管理员）** 按 `region_id` 管辖本区域，可管本区域的学校/教研/学情/错题/组卷/批改/周报/合规，但**不可**触碰系统设置（菜单/角色/区域/厂商为平台级，归 admin）。
> - **school（学校）** 仅管本校数据 + 只读已分配厂商。
> - **teacher（教师）** 教学侧（本班）。
> - **parent（家长）** 只读子女。
> - **student（学生）** 不进 Web 后台，仅 App 端，不作为 Web 菜单角色（其 App 端功能由 App 用户体系承载，parent↔student 绑定在 app 域处理）。
> - 按钮级（如"新建菜单""删除菜单"）只在 admin 的菜单管理下授权；region_admin 对学校管理类操作按区域授权。

## 十、系统服务（MCP）商业化：有效期 · 续期 · 支付

> **需求**：系统 MCP 能力要有**正式使用有效期**，过期后能力失效；提供**续期充值**能力，支持**微信 / 支付宝**支付。
> **性质**：本节能把 P5「计费对账」的一小块**提前拉入本期**（与 BYOM 同理），但仅限"MCP 服务订阅续期"这一闭环，完整计费对账仍归 P5。

### 10.1 需求拆解

| 用户要求 | 对应系统能力 |
|---|---|
| MCP 能力有正式使用有效期 | `mcp_service_subscription`：`valid_from` / `valid_until` / `status`，按「厂商 × 作用域」订阅 |
| 过期后 MCP 能力失效 | 调用前拦截 + 定时扫描置 `expired` + 管理台剩余天数/到期预警；支持宽限期 `grace_days` 与 `expiry_action`（disable/readonly） |
| 续期充值 | 选套餐 → 生成续期订单 → 扫码支付 → 回调验签 → 延长 `valid_until` → 能力恢复 |
| 微信 / 支付宝 | 微信支付 **Native 扫码**（API v3）、支付宝 **当面付 `alipay.trade.precreate`**，二者均为"出二维码→用户扫→异步回调" |

### 10.2 作用域模型（复用既有 scope 概念）

订阅挂在 **厂商 × 作用域** 上，与功能开关（§八-4）同构，便于按角色续期：
```
global(平台, admin 续期)  >  region(区域, region_admin 续期)  >  tenant(学校, school 续期)
```
- 默认走 **platform 级订阅**（admin 续期，符合 D1：系统服务仅 admin 可管）。
- 若后续开放"学校自费续期"，只需按 `scope_type=tenant` 落一条订阅，无需改模型。

### 10.3 有效期与失效

- **生效判定**：`now BETWEEN valid_from AND valid_until AND status='active'` → 可用。
- **强制点**（三道，缺一不可）：
  1. **调用前拦截**：MCP 网关/DAO 在路由到该厂商前校验有效期，过期直接拒绝（安全边界在服务端）。
  2. **定时扫描**：定时任务把过期订阅置 `expired`，并停用其 `mcp_service_instance`。
  3. **管理台呈现**：显示剩余天数；**提前 7 天**预警（站内 + 可选邮件/短信）。
- **策略**：`expiry_action` 默认 `disable`（停用）；可选 `readonly`（降级只读）。`grace_days` 默认 `0`（可配 3/7 天宽限，宽限内可用但持续提醒）。

### 10.4 续期充值流程（微信 / 支付宝）

```
管理台「续期」
   → 选套餐（mcp_service_plan：月卡/年卡，时长+价格）
   → POST /api/admin/mcp/orders  （服务端按 plan_id 定价，绝不采信客户端金额）
   → 调支付渠道下单：
        微信 Native(v3) → code_url
        支付宝 precreate → qr_code
   → 前端渲染二维码，轮询 GET /api/admin/mcp/orders/{order_no}
   → 用户扫码支付
   → 支付方异步回调 POST /api/pay/notify/{wechat|alipay}
        ├ 验签（微信：平台证书 + AES-256-GCM 解密 resource；支付宝：RSA2 公钥验签）
        ├ 幂等（同 order_no 已 paid 则直接回成功，防重复回调）
        └ 成功后延长 valid_until、置 order=paid、写 notify 流水
   → 前端轮询到 paid → 能力恢复
```
**兜底**：回调可能丢失/延迟 → 除轮询外，服务端提供**主动查单**补偿（调微信/支付宝查单接口），避免"付了钱没续上"。

### 10.5 数据模型（新增 4 表）

```sql
-- 14) 套餐/定价
CREATE TABLE mcp_service_plan (
    plan_id       VARCHAR(64) PRIMARY KEY,
    vendor_id     VARCHAR(64) REFERENCES sys_service_vendor(vendor_id),
    plan_name     VARCHAR(128) NOT NULL,        -- 月卡 / 年卡 / 三年卡
    duration_days INT          NOT NULL,        -- 30 / 365 / 1095
    price_cny     NUMERIC(10,2) NOT NULL,       -- 服务端定价唯一来源
    status        SMALLINT     DEFAULT 1
);

-- 15) 订阅（有效期核心）
CREATE TABLE mcp_service_subscription (
    sub_id       VARCHAR(64) PRIMARY KEY,
    vendor_id    VARCHAR(64) NOT NULL REFERENCES sys_service_vendor(vendor_id),
    scope_type   VARCHAR(16) NOT NULL,          -- global / region / tenant
    scope_id     VARCHAR(64),
    valid_from   TIMESTAMPTZ NOT NULL,
    valid_until  TIMESTAMPTZ NOT NULL,          -- 过期点
    status       VARCHAR(16) DEFAULT 'active',  -- active / expired / disabled
    expiry_action VARCHAR(16) DEFAULT 'disable',-- disable / readonly
    grace_days   INT         DEFAULT 0,
    created_at   TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ix_sub_vendor_scope ON mcp_service_subscription(vendor_id, scope_type, scope_id);

-- 16) 续期订单
CREATE TABLE mcp_renewal_order (
    order_no      VARCHAR(64) PRIMARY KEY,
    sub_id        VARCHAR(64) NOT NULL,
    plan_id       VARCHAR(64) NOT NULL,
    amount_cny    NUMERIC(10,2) NOT NULL,       -- 由 plan 定价，非客户端传入
    duration_days INT          NOT NULL,
    channel       VARCHAR(16) NOT NULL,         -- wechat / alipay
    status        VARCHAR(16) NOT NULL,         -- pending / paid / closed / failed / refunded
    qr_code_url   TEXT,                          -- 二维码内容/链接
    trade_no      VARCHAR(128),                  -- 第三方交易号
    expire_at     TIMESTAMPTZ,                   -- 订单支付超时（默认 15 分钟关闭）
    paid_at       TIMESTAMPTZ,
    created_by    VARCHAR(64),
    created_at    TIMESTAMPTZ DEFAULT now()
);

-- 17) 支付回调流水（幂等 + 审计）
CREATE TABLE mcp_payment_notify (
    notify_id   VARCHAR(64) PRIMARY KEY,
    order_no    VARCHAR(64) NOT NULL,
    channel     VARCHAR(16) NOT NULL,
    raw_payload JSONB,
    verified    BOOLEAN DEFAULT FALSE,          -- 验签结果
    processed   BOOLEAN DEFAULT FALSE,          -- 幂等标记
    received_at TIMESTAMPTZ DEFAULT now()
);
```

### 10.6 网关改造（硬约束 · 已核实）

| **T-B4** | 支付回调：网关 `/api/pay/notify/` 免鉴权路由 + web-backend `/api/pay` 挂载 + 验签（微信平台证书/AES-GCM、支付宝 RSA2）+ 幂等 + 延长 `valid_until`；**主动查单补偿** | T-B3 | 高 |
| **T-B5** | 管理台续期页：套餐选择、二维码支付、状态轮询、有效期与剩余天数展示、到期预警 | T-B3, T-B4 | 中 |
| **T-B6** | 单测 + 联调 + 安全：过期拦截、金额篡改无效、伪造回调被拒、重复回调幂等、密钥加密落库与日志脱敏；微信/支付宝**沙箱**跑通全链路 | T-B2~T-B5 | 中–高 |

### 10.8 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 回调丢失/延迟导致"付了没续上" | 高 | 轮询 + **主动查单补偿**（T-B4），以支付方为准 |
| 金额被篡改（客户端传低价） | 高 | 金额**服务端按 `plan_id` 定价**，客户端仅传 `plan_id` |
| 伪造回调（绕过支付直接续期） | 高 | 回调**必须验签**（微信平台证书 + AES-256-GCM；支付宝 RSA2）；免鉴权路由另加限流 |
| 重复回调重复延长有效期 | 中 | `mcp_payment_notify.processed` 幂等标记 + 订单状态前置校验 |
| 商户密钥泄露 | 高 | API v3 Key / 商户私钥 / 支付宝私钥走 AES-256-GCM 凭证库加密，日志脱敏（与 BYOM 同款） |
| 商户资质与域名备案 | 中 | 需企业商户号并把 `sd12sd.icu` 配入支付平台 notify 白名单；**先跑沙箱**（T-B6） |
| 时区/时钟导致有效期误判 | 低 | 全部 `TIMESTAMPTZ` 存 UTC，前端按本地时区展示 |

### 10.9 验收标准

- ✅ MCP 订阅有起止有效期；**未过期可用、过期即被拦截**（调用返回失效），管理台显示剩余天数。
- ✅ 到期前 7 天出现预警；`grace_days`/`expiry_action` 配置生效。
- ✅ 管理台可发起续期：选套餐 → 出二维码（微信/支付宝）→ 完成支付 → 回调后 `valid_until` 延长、能力恢复。
- ✅ 伪造回调被拒（验签失败不续期）；重复回调不重复延长；篡改金额无效。
- ✅ 支付回调经 `/api/pay/notify/` 免鉴权路由可达，且该路径不被 `/api/admin/` 的 rbac 拦截。
- ✅ 商户密钥加密落库，日志与响应不含明文密钥/凭证。
