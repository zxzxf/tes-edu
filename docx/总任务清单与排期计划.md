### 3.6.1 T-VLM：学生端视觉模型（拍照识题）从学校 BYOM 配置取（已完成）

**背景**：此前拍照识题的 VLM 只读全局 env（`VLM_BASE_URL / VLM_MODEL / LLM_API_KEY`），学校无法自行开通；且每次请求都要打 Redis/PG 查配置，性能不够。现已改为：**所有面向学生端的模型变量（chat / embedding / VLM）都从学校 BYOM 配置取，配置缓存落本地 SQLite**。

#### （1）后端改动摘要

- **数据库**：`tenant_model_config` 新增两列（已在 137 的 106 库执行迁移 `0003_tenant_vlm.sql`）：
  - `vlm_base_url text`：视觉模型端点 base URL（可空，缺省复用该校 chat 段的 `base_url`）
  - `vlm_model varchar(128)`：视觉模型名（如 `qwen-vl-max` / `gpt-4o` 等）
  - **密钥复用该校 chat 段的 `api_key_enc`**，不另存一列
- **agent 解析**：`resolve_llm_config(tenant_id)` 返回的 `LLMConfig` 增加 `vlm_base_url / vlm_model` 字段；租户未配 `vlm_model` 时回落平台全局 env（保留接入 BYOM 前的行为）
- **RAG & 缓存**：`rag.retrieve` 与 `llm_cache.cached_solve` 的近似命中分支也按租户配置的 embedding 模型向量化（保证向量空间一致）
- **配置缓存**：原 Redis 主缓存替换为 **本地 SQLite**（`_SqliteCache`，WAL + busy_timeout，标准库 `sqlite3` + 线程池），默认路径 `/app/data/byom_cache.db`，可通过 `BYOM_CACHE_DB` 环境变量覆盖；查询亚毫秒级，不再每次请求都打 Redis/PG
- **密钥不落盘（方案 A）**：写入 SQLite 的缓存值**刻意剔除 `chat_api_key` / `embed_api_key`**，缓存命中时再从 DB 解密回填。SQLite 文件即使被拖走也拿不到密钥。详见下方（5）

#### （5）密钥安全口径：为什么 SQLite 里没有 API Key（方案 A）

**结论：模型密钥绝不写进 SQLite，也不写进任何本地文件。**

| 环节 | 密钥在哪 | 形态 |
|---|---|---|
| 持久化 | 106 PG 库 `tenant_model_config.api_key_enc` | **AES-256-GCM 密文**（密钥来自 env `VENDOR_CREDENTIAL_KEY`） |
| 运行态 | `resolve_llm_config()` 解密后放入 `LLMConfig` | 明文，仅驻留单次请求的内存 |
| 缓存 | 本地 SQLite `byom_cfg_cache` | **不含密钥**（写入前剔除 `*_api_key` 字段） |
| 前端 | B 端列表页 | 仅显示掩码，编辑时不回显明文 |

**为什么这么设计**：SQLite 缓存文件落在容器磁盘（`/app/data/`），一旦容器被攻破、镜像层被导出、或目录被挂载出来，里面如果有明文密钥就是一次全量泄露。剔除密钥后，即使文件被完整拖走，攻击者也只能拿到"学校用了哪个模型、端点在哪"——不含任何可用于调用的凭证。

**代价（明确记录）**：缓存命中时仍需查一次库把密钥解密回填，约 3~5ms。相比 LLM 调用动辄几百毫秒，这个代价可以忽略；换来的却是"密钥零落盘"。

**兜底**：缓存命中路径若发现租户已被删除/禁用，会主动删掉这份脏缓存并回落全局配置（不会因缓存缺 key 而抛 `TypeError`）；同时对缓存里的 base_url 复跑一遍 SSRF 闸门，防止缓存文件被篡改后指向内网地址。

**红线单测**（`tests/test_tenant_llm.py`）：
- `test_cache_never_persists_api_key`：断言写入 SQLite 的值不含任何 `api_key` 字段，且明文密钥不出现在序列化结果里
- `test_cache_hit_refills_key_from_db`：断言缓存命中能回填密钥、租户禁用时缓存失效回落全局

#### （6）额度告警排查指引（403 / 429 / 答案降级）

**核心认知**：额度耗尽时系统**故意不报错**——`rag.retrieve` 与 `llm.solve` 都做了降级，HTTP 仍是 200。所以"接口不报 500"不等于"系统健康"，必须靠下面的流程主动发现。

**① 现象 → 含义对照表**

| 现象（学生端 / 接口） | 判定字段 | 常见根因 |
|---|---|---|
| 解题 200，但答案像模板、无引用来源 | 响应 `degraded: true` | Chat 段 403/429，走 `_dev_answer` 模板降级 |
| 解题 200，有答案但 `knowledge_points` 为空、相似例题变少 | RAG 内部 `degraded`（**只在日志可见**，不直接下发给前端） | **Embedding 段 429** —— 向量化失败，检索三级降级返回空 |
| 拍照识题 200，但提示"该租户未配置视觉模型"或识别失败 | `degraded: true` / `healthz.vlm: false` | VLM 段未配（`vlm_model` 空）或 403/429 |
| 触类旁通为空 | `similar_degraded: true` | 主解可用、变式生成那次 LLM 调用失败（同 Chat 段额度） |
| 请求迟迟不返回 / 网关超时 | — | 该模型在长 prompt 上挂起（实测 `deepseek-v4-pro` 解答题长 prompt 不返回） |

**② 三步定位**

1. **看响应**：`curl -s https://sd12sd.icu/healthz`（看 `llm` / `embed` / `vlm` 三个布尔位）；或直接调 `/api/app/solve`，看返回的 `degraded`、`similar_degraded`。
2. **看日志**（拿真实错误码，最关键的一步）：
   ```bash
   ssh 137 "docker logs --tail=500 edu-agent-backend 2>&1 | grep -iE '403|429|quota|rate limit|degraded'"
   ```
   Embedding 失败会打 `rag ... degrade to empty`，租户维度问题会带 `tenant_id`。
3. **看用量表**（判定是"偶发抖动"还是"彻底没钱了"）。本地先建隧道 `ssh -N -L 15432:106.12.25.5:5432 137`：
   ```sql
   SELECT model, error_kind, count(*) AS n, max(created_at) AS last_at
   FROM llm_usage
   WHERE created_at > now() - interval '6 hours'
   GROUP BY model, error_kind
   ORDER BY n DESC;
   ```
   `error_kind` 口径（`usage.classify_error`）：**`quota`** = 含 403 / quota / rate limit / 429；`timeout`；`other`；成功为 `NULL`。
   > 注：`llm_usage` **没有租户列**（建表时未加），定位"是哪所学校"只能回到第 2 步的 agent 日志。B 端概览接口：`GET /api/admin/llm-usage`、`GET /api/admin/llm-usage/budget`。

**③ 错误码 → 处置**

| 错误码 / 现象 | 性质 | 处置 |
|---|---|---|
| `403 Free quota exhausted` | **硬配额，不会自行恢复** | 换模型（优先 `qwen3.8-flash`）/ 换端点 / 充值。**历史坑**：`qwen3.8-max`、`deepseek-v4.1-flash` 曾持续 403，勿配 |
| `429 Too Many Requests` / workspace budget | 滚动限流或工作空间日预算耗尽 | 短时抖动等几分钟自恢复；全天不行按 403 处置 |
| 无响应 / 挂起 | 模型侧长 prompt 问题 | 换短输出模型；跑批脚本有 300s 超时 + 重试 |
| Embedding 429（**最常见**） | RAG 降级，主解仍可用 | 把该校 Embedding 段**留空**回落全局 `qwen3.7-text-embedding`，或换端点 / 充值 |
| VLM 403/429 | 拍照识题不可用 | 实测 `qwen3.8-omni-flash` 可用，换它或充值 |

**④ 两个必踩的坑**

- **配置缓存 TTL 120s**：改完配置要点一次"保存并测试"主动失效缓存，否则最多要等 `BYOM_CONFIG_TTL`（默认 120s）才生效。排查期别把"改了没生效"误判成额度问题。
- **降级结果绝不进缓存**（`llm_cache.cached_solve` 明确跳过，红线单测 `test_degraded_result_is_not_cached`）。所以额度恢复后**新题立刻正常**；但额度耗尽前已缓存的成功结果仍在 TTL 内——验证时必须换一道**没问过的新题**，否则会看到假阳性。

**⑤ 恢复验证（三步）**

1. 后台改完配置 → "保存并测试"三项全绿；
2. 换一道**新题**连打两次：第一次 `degraded: false` 且 `knowledge_points` 非空，第二次应命中缓存（秒回）；
3. 再跑一遍第 ② 步日志命令，确认最近 30 分钟无新增 `quota`。

**⑥ 预防配置（T-D3）**

agent / web 两侧 `.env` 配：`LLM_DAILY_BUDGET`（元）、`LLM_BUDGET_WARN_RATIO`（告警水位）、`LLM_BUDGET_ACTION`（`alert` 只告警 / `force_simple` 强制走便宜模型）；单价用 `LLM_COST_PER_1K_TOKENS_IN/OUT` + `LLM_MODEL_PRICES`（按模型覆盖）。超水位时日志打 `[budget-audit] state=warn|over used=... budget=...`，可据此接告警采集，不必等用户反馈才发现额度打满。
