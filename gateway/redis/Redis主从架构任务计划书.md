# Redis 主从架构任务计划书（137 ↔ 106）

> 范围：把 137 服务器与 106 服务器上已有的两套 Redis 组建成 **一主一从** 异步复制拓扑，提供冗余（DR）+ 读扩展。
> 适用版本：两端均为 `redis:7-alpine`，原生支持 `replicaof` 主从。

---

## 一、背景与现状

| 节点 | 容器 | 镜像 | 监听 | 口令 | 当前用途 |
|------|------|------|------|------|----------|
| **106**（百度云 `106.12.25.5`） | `srv-redis` | `redis:7-alpine` | `0.0.0.0:6379`（公网 + iptables DOCKER-USER 白名单 137） | `Tes@Redis#106`（env 注入） | 数据层缓存 / 会话 / 限流 |
| **137**（腾讯云 `124.221.253.137`） | `edu-redis` | `redis:7-alpine` | `10.0.0.5:6379`（仅 edu-net 内网） | 待确认（配置占位 `changeme`） | 网关限流令牌桶 / 配置 PubSub 热更新 |

**已具备的条件**
- 106 的 `srv-redis` 已对 137 公网 IP 做 iptables 白名单（与 5432 同源），137→106 公网链路已实测连通。
- 两端均 `appendonly yes`（AOF 持久化）。
- 阿里云 ACR（`registry.cn-shanghai.aliyuncs.com/mis_ser`）两端均已 `docker login`。

---

## 二、可行性结论

✅ **完全可行。** 两端版本一致、均支持主从复制，且 106:6379 已对 137 放开。

⚠️ **必须正视的三个约束**

1. **写路径约束**：137 网关的限流令牌桶、配置 PubSub 都依赖 Redis **写入**。若 137 作为只读副本，网关写会直接失败 → **主节点必须落在「写入发生侧」**。
2. **跨云复制默认明文**：Redis 主从复制不加密，跨公网传输有被嗅探风险 → 短期靠「强口令 + 源 IP 白名单」兜底，中期上 TLS/stunnel。
3. **137 的 redis 仅内网可达**（`10.0.0.5`，未对公网映射）。106 副本无法反向连入 137 → 因此 **106 作主、137 作从** 是最省事、无需新开公网端口的方向。

---

## 三、推荐架构（106 主 / 137 从）

```
              ┌─────────────── 137 腾讯云 ──────────────┐
              │  gateway (限流 / 配置)                    │
              │     │ 读写 ─┐  (跨云公网, 白名单)         │
              │     ▼       │                            │
              │  edu-redis (REPLICA 只读, 10.0.0.5:6379) │
              └─────────────┼────────────────────────────┘
                            │ replicaof 106.12.25.5 6379
                            ▼
              ┌─────────────── 106 百度云 ──────────────┐
              │  srv-redis (MASTER 读写, 0.0.0.0:6379)   │
              │   requirepass + iptables 白名单 137      │
              └──────────────────────────────────────────┘
```

- **主（106 `srv-redis`）**：保留现有强口令、AOF、`0.0.0.0:6379` 公网映射 + 白名单。
- **从（137 `edu-redis`）**：改为 `replicaof 106.12.25.5 6379` + `masterauth <同主口令>` + `replica-read-only yes`，重启容器。
- **网关写入**：限流/配置仍走 Redis，但客户端地址需指向 **106 主**（跨云一次 RTT，限流增量可接受；若延迟敏感，见第七节备选）。

---

## 四、实施任务

### P0 前置（网络 / 安全 / 口令）
- [ ] **确认 106 iptables 白名单含 6379**（沿用现有白名单脚本，现仅确认放行了 137→106:5432；需补 6379 或复用同条规则）。
- [ ] **统一强口令**：主从共用同一强口令；137 当前为占位 `changeme`，必须替换，且**不得落库到 git**（走 env / secret）。
- [ ] **（P2）复制链路加密**：用 stunnel 在 106:6379 ↔ 137:6379 之间做 TLS 隧道，消除公网明文复制风险。

### P1 主从搭建
- [ ] **106 主**：确认配置
  ```ini
  bind 0.0.0.0
  port 6379
  requirepass <强口令>
  appendonly yes
  appendfsync everysec
  ```
- [ ] **137 从**：修改 `edu-redis` 启动配置
  ```ini
  replicaof 106.12.25.5 6379
  masterauth <同主口令>
  requirepass <同主口令>
  replica-read-only yes
  appendonly yes
  ```
  重启容器生效。
- [ ] **验证复制**
  ```bash
  # 137 上
  redis-cli -h 10.0.0.5 INFO replication
  # 期望：role:slave  master_host:106.12.25.5  master_link_status:up
  # 106 上写入，137 上能读到
  redis-cli -h 106.12.25.5 -a <pwd> SET __repl_probe 1
  redis-cli -h 10.0.0.5     -a <pwd> GET __repl_probe   # => "1"
  ```

### P2 应用接入与高可用
- [ ] **网关 redis 客户端**指向 **106 主**（写）或经统一配置中心；调整 gateway `config.yaml` 中 store/limit 地址。
- [ ] **（可选）Redis Sentinel ×3** 实现自动故障切换（主宕机自动提升 137 为从→主）。本期先**人工切换**预案。
- [ ] **监控**：复制延迟 `master_repl_offset` / `slave_repl_offset` 差值、复制中断（`master_link_status:down`）告警。

---

## 五、回滚预案
- 去掉 137 的 `replicaof`，重启 `edu-redis` 恢复为独立主节点 → 本地限流/配置继续工作，业务不受 106 影响。
- 106 主若宕机：临时把网关 redis 指回 137（需先把 137 的 `replica-read-only` 关掉并提升为主）。

---

## 六、风险与待确认
| 风险 | 说明 | 缓解 |
|------|------|------|
| 跨云写延迟 | 网关限流 token 增量走公网（137→106） | 评估是否限流改本地内存；或采用第七节备选 |
| 明文复制 | 公网主从复制未加密 | P2 上 stunnel/TLS |
| 口令轮换 | 改口令需同步 `requirepass` / `masterauth` | 用同一 secret 注入两端 |
| 137 redis 口令未知 | 当前为 `changeme` 占位 | 上线前确认并改为强口令 |

---

## 七、备选方案（137 主 / 106 从）
若跨云写延迟不可接受，可反过来：
- 把 **137 `edu-redis`** 暴露公网（`bind 0.0.0.0` + 安全组白名单 106）→ **137 作主**，**106 作从**。
- 优点：网关写本地亚毫秒，无跨云 RTT。
- 缺点：需新开 137:6379 公网端口；106 从只读，106 本地写缓存需改走 137 主。

> 结论：默认采用 **第三节（106 主 / 137 从）**；仅在压测证明跨云限流延迟不可接受时，切换到第七节备选。
